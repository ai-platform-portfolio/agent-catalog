# Agent knowledge and SRE investigation: market research

**Research date:** 7 November 2026. **Status:** design research, not a deployed capability or an implementation decision. Public engineering accounts are selective disclosures; vendor-reported results are not independent, comparable market-share measurements.

This note supports [the reusable agent platform design](AGENT_PLATFORM_DESIGN.md). The first agent is an SRE agent, but its knowledge and investigation interfaces should be reusable by later custom agents in Foundry.

## Terms and central finding

**Retrieval-augmented generation (RAG)** means retrieving relevant external information before an agent answers or acts. Retrieval can use exact search, semantic search, SQL, a graph, or live APIs; it does not require a vector database. **Hybrid retrieval** combines exact keyword matching with semantic matching using embeddings (numeric representations of meaning). Exact search is valuable for error strings, resource names and configuration keys; semantic search finds related material expressed in different words.

The strongest public evidence points to a combination of live evidence, searchable documents and code, curated domain knowledge, and verified system relationships. A single search product is unlikely to answer all SRE questions well.

## Retrieval and storage choices

**Azure AI Search** supplies a managed, separate search index with hybrid queries and semantic ranking. Foundry IQ builds on Azure AI Search. This is a strong candidate for a multi-source document corpus when managed indexing and Foundry integration justify a separate service. Index freshness, access-control synchronization, cost and ingestion still need design and measurement. Azure's generally available agentic retrieval API provides minimal extractive retrieval; LLM query planning and answer synthesis use a preview API as of this research date. [Azure RAG guidance](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview); [agentic retrieval availability](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview); [Foundry IQ FAQ](https://learn.microsoft.com/azure/ai-foundry/agents/concepts/foundry-iq-faq).

**PostgreSQL with pgvector** is a genuine production alternative, especially when documents and their permissions or operational metadata already live in PostgreSQL, and freshness or relational filtering matter. pgvector supports exact and approximate vector search; PostgreSQL also supplies full-text search. The application must implement and tune more of the hybrid fusion, reranking and ingestion pipeline. Microsoft's own architecture guide includes Azure Database for PostgreSQL among its vector-search options. Do not dismiss it as a prototype database or assume it wins without workload measurements. [Microsoft service comparison](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/vector-search); [pgvector](https://github.com/pgvector/pgvector).

**A knowledge graph** represents entities and their relationships. For SRE, authoritative edges such as service-to-owner, workload-to-release and service-to-database can support upstream cause and downstream impact queries. **GraphRAG** uses graph relationships during retrieval and may extract them from documents using an LLM. An operational topology built from versioned or live source systems is a different, more immediately testable asset than an automatically inferred document graph. A dedicated graph database should be justified by actual multi-hop query needs and freshness requirements, rather than added by default. [Netflix's metadata graph](https://netflixtechblog.com/democratizing-machine-learning-at-netflix-building-the-model-lifecycle-graph-5cc6d5828bb1); [PagerDuty's topology approach](https://www.pagerduty.com/eng/lessons-from-pd-labs-from-experimentation-to-a-production-ready-sre-agent/); [Microsoft GraphRAG research project](https://github.com/microsoft/graphrag).

## Proposed portfolio approach

1. Use constrained **live diagnostic tools** for current AKS, Argo CD, Azure and observability state. Return bounded, timestamped evidence with source links. A document index must not be treated as the source of truth for current cluster health.
2. Use **hybrid RAG** for runbooks, architecture decisions, prior incidents and operational procedures. Record document owner, version, access scope and update time. Search code with exact and semantic methods appropriate to code, rather than only document embeddings.
3. Build a **service topology** from existing Backstage, GitOps, Kubernetes and Azure metadata where those sources are authoritative. Preserve the source and freshness of each edge. Add inferred relationships only with an explicit confidence and verification path.
4. Keep the agent's retrieval and diagnostic tool contracts independent of the backing search store. Compare AI Search and pgvector on the same corpus and cases before selecting a knowledge-store dependency. This is a proposed design direction, not a commitment to deploy both.
5. Evaluate GraphRAG only if measured multi-hop failures remain after using authoritative topology and hybrid retrieval. Adding a graph store has ongoing ingestion, consistency and operating costs.

**Offline evaluation** is a repeatable test on versioned past incidents and questions with expected evidence and outcomes. **Online evaluation** observes sampled real or controlled live investigations after release. Measure retrieval recall, citation correctness, source freshness, fault localization, causal diagnosis, misdirection, justified abstention, fix effectiveness, latency and cost. Incident replay can miss details available in the original incident; live fault injection gives stronger end-to-end evidence. Human SRE review remains necessary for disputed diagnoses and proposed fixes. [PagerDuty's benchmark method and limits](https://www.pagerduty.com/eng/lessons-from-pd-labs-from-experimentation-to-a-production-ready-sre-agent/); [Uber's curated test set](https://www.uber.com/rs/en/blog/enhanced-agentic-rag/).

## Open decisions

- Which runbooks and incidents form the first permission-safe, versioned evaluation corpus?
- Which questions require live tools, document retrieval, code search or topology traversal?
- Does the corpus and its update rate favour a managed search index or an existing durable PostgreSQL service? A disposable cluster database would not preserve knowledge across teardown.
- Which managed SRE product can be tested on the same incidents and evidence access, rather than compared through vendor claims?

No knowledge store, topology service or SRE retrieval tool is deployed by this note.
